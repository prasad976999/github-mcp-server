The 30-second pitch

"I built an MCP server in Python that gives AI assistants like Claude safe, structured access to GitHub. It can search repositories, fetch details, browse folders, read source files, and list issues and pull requests. It uses all three MCP primitives: tools, a README resource, and prompts for summarising a repository and reviewing a pull request. I used the official MCP Python SDK, an async httpx client for the GitHub REST API, and Pydantic models to keep outputs small and typed. I focused on tool design: clear names and descriptions, input validation, error messages the model can act on, and guards so large files or long lists never flood the model's context. It retries temporary failures with exponential backoff and handles GitHub's rate limits without hanging. Its one write tool, create_issue, is off by default, marked as non-read-only so hosts ask the user first, and never retried blindly. It's covered by tests that mock GitHub, so they run offline in about two seconds, and GitHub Actions runs lint and the tests on Linux and Windows across three Python versions on every push, with a 90% coverage floor. It runs locally over stdio, or as a Docker container serving Streamable HTTP, protected by a bearer token and DNS rebinding checks."

The 2-minute walkthrough

When an interviewer says "walk me through your project":

  1. What MCP is. An open protocol that standardises how AI applications connect to tools and data. You wrap a service once as an MCP server, and any MCP host can use it.
  2. Architecture. The host (Claude Desktop or Claude Code) launches my server as a subprocess and talks JSON-RPC over stdin/stdout. It can also run as an HTTP service in Docker, with the same tools. My server has three layers: the MCP layer (server.py) defines the tools, the API layer (github_client.py) does HTTP, and the models layer (models.py) shapes what the model sees.
  3. Tools. search_repositories, get_repository, list_directory, get_file_contents, list_issues, list_pull_requests, get_rate_limit, server_status, and the write tool create_issue. Plus a resource (github://repos/{owner}/{repo}/readme) and two prompts (summarize_repository, review_pull_request).
  4. Engineering decisions. One shared async HTTP client created in the server's lifespan; outputs trimmed from ~100 fields to ~13; pagination that follows GitHub's Link headers with a 5-page cap; files cut off at a limit with an explicit truncated flag; network errors and 5xx retried with exponential backoff and jitter, rate limits waited out only when the wait is short; writes off by default and never retried after a 5xx; every failure turned into a readable tool error; a fine-grained read-only token loaded from the environment.
  5. Testing. pytest with respx to fake GitHub (including 404s, timeouts, server errors, rate limits, binary and oversized files), calling tools through the SDK's in-process client exactly as a real host would. CI on GitHub Actions runs lint and tests on 2 operating systems × 3 Python versions on every push and pull request, fails if coverage drops below 90%, and builds and starts the Docker image.
  6. Deployment. A multi-stage Docker image running as a non-root user with a health check. In HTTP mode the server listens on loopback by default, refuses to listen anywhere else without a bearer token, and rejects unknown Host headers.

Step 1 Scaffold and first tool a real MCP server that an AI client can connect to and call, with one tool. No GitHub calls yet; we prove the wiring first.

1. What MCP is (the 30-second interview answer)

MCP (Model Context Protocol) is an open protocol, created by Anthropic, that standardises how AI applications connect to external tools and data. Before MCP, every AI app wrote its own integration for every service (N apps x M services). With MCP, a service is wrapped once as an MCP server and any MCP host (Claude Desktop, Claude Code, IDEs, other agents) can use it. People call it "USB-C for AI tools".

Three roles:

  • Host: the AI application the user talks to (Claude Desktop, Claude Code).
  • Client: a component inside the host that holds one connection to one server.
  • Server: our program. It exposes capabilities and does the real work (calling GitHub).

Messages are JSON-RPC 2.0. The host starts by asking the server what it offers (initialize, then tools/list), and the model decides when to call a tool (tools/call).

2. The three server primitives

Primitive Who controls it Example in this project
Tool The model decides to call it search_repositories, create_issue
Resource The application/user attaches it as context github://repos/{owner}/{repo}/readme
Prompt The user picks it (like a slash command) review_pull_request

This distinction is a very common interview question. Short answer: tools are model-controlled actions, resources are application-controlled read-only data, prompts are user-controlled templates.

3. Transports

  • stdio (what we use now): the host launches our server as a subprocess and talks over stdin/stdout. Simple, local, no network port, the token never leaves the machine.
  • Streamable HTTP: the server runs as a web service, many clients connect over HTTP. Needed for remote/multi-user deployments (we add it in step 8).

Consequence of stdio that trips people up: stdout is the protocol channel. Any print() corrupts the JSON-RPC stream. That's why server.py sends logs to stderr.

5. The code, line by line

config.py

  • SecretStr wraps the token so it prints as ********** if it ever ends up in a log or traceback. Small detail, good interview point about secret hygiene.
  • Settings come from environment variables because the MCP host passes secrets to the server that way (the env block in the client config). Never hard-code tokens, never commit .env.
  • request_timeout_s: Field(gt=0): Pydantic validates config at startup, so a bad value fails fast instead of mid-request.

server.py

  • MCPServer(name=..., instructions=...): the high-level server class in MCP Python SDK v2 (in v1 it was called FastMCP; many tutorials online still show v1, so you can mention you used the current v2 API). instructions is sent to the host during initialize and helps the model understand how to use the server as a whole.
  • @mcp.tool(): registers a function as a tool. The SDK reads the function name (tool name), docstring (tool description the model sees), type hints (JSON Schema for the inputs) and return type (output schema). This is the key idea of "tool design": your docstring and parameter names are the prompt the model uses to decide when and how to call the tool.
  • Returning a Pydantic model (ServerStatus) instead of a plain dict gives the client structuredContent with a declared output schema, so the model and client get typed, predictable data. (Our first test caught exactly this: a bare dict produced no structured output.)
  • mcp.run() defaults to the stdio transport.

tests/test_server.py

  • Client(mcp) connects to the server in-process, no subprocess or network. The test does exactly what a host does: list tools, call one, check the result. Fast and deterministic.

8. Interview questions for this step

  1. What problem does MCP solve? The N x M integration problem; one standard protocol between AI apps and tools/data.
  2. Host vs client vs server? Host = AI app; client = one connection inside the host; server = exposes tools/resources/prompts.

1. The big idea: layers

tool function (server.py)  →  GitHubClient (github_client.py)  →  GitHub REST API
        ↑ returns a Pydantic model (models.py)
  • server.py knows about MCP: tool names, descriptions, inputs, errors the model should see. It contains no URLs or headers.
  • github_client.py knows about HTTP: base URL, auth header, timeouts, turning failed responses into one exception type.
  • models.py decides what data the model actually gets back.

Interview line: "I separated the protocol layer from the API layer, so I can test each on its own and swap the transport or the API without touching the other."

2. github_client.py

Headers - Accept: application/vnd.github+json and X-GitHub-Api-Version: 2022-11-28: GitHub recommends both. Pinning the API version means a future GitHub change can't silently break us. - User-Agent: GitHub rejects requests without one. - Authorization: Bearer <token>: only added when a token exists. Without a token GitHub allows 60 requests/hour per IP; with one, 5,000/hour. That's the main reason to use a token even for public data.

One shared httpx.AsyncClient - Created once, reused for every call. It keeps a connection pool: the TCP + TLS handshake (often 100ms+) happens once, not on every request. - Async because MCP servers handle requests concurrently. While one tool waits on GitHub, the server can work on another request instead of blocking. This is I/O-bound work, which is exactly where async helps. - Timeout (15s default): never let a hung network call hang the model's turn forever.

Error mapping - Every failure (timeout, network error, 401, 403, 404, 422, 5xx) becomes one GitHubAPIError with a plain-English message plus the HTTP status. The message is written for the model to read, because the model is the one that decides what to do next (fix a typo in the repo name, ask the user for a token, try a different query).

3. models.py: why trim the output?

A raw GitHub repository response has around 100 fields, most of them URLs. Every field costs tokens in the model's context window and adds noise. Repository.from_api() keeps around 13 useful ones.

Returning a Pydantic model (not a dict) also gives the client an output schema and structuredContent, so the model gets typed, predictable fields. Repository extends RepoSummary, so search results stay short and the detailed view adds more.

Interview line: "Tool output design is context engineering. I return the smallest useful shape, and a search tool returns summaries with a separate get tool for details."

4. server.py

Lifespan

@asynccontextmanager
async def lifespan(_server):
    github = GitHubClient(settings)
    try:
        yield AppContext(github=github)
    finally:
        await github.aclose()

Code before yield runs at startup; code after runs at shutdown. The yielded AppContext is available to every tool through ctx.request_context.lifespan_context. This is dependency injection: tools don't create their own client, they receive a shared one, and connections are closed cleanly when the server stops.

ctx: Context: a parameter typed as Context is injected by the SDK and hidden from the model. It isn't part of the tool's input schema.

Tool design choices (the "tool design" learning goal from your image): - Names are verbs plus nouns (search_repositories, get_repository), matching how the model thinks about the task. - Docstrings say what the tool returns and when to use another tool ("call get_repository for full details"). - Annotated[str, Field(description=...)] puts a description and examples on each parameter. The search description teaches GitHub query syntax (language:python, stars:>1000), which makes the model write much better queries. - Field(ge=1, le=30) on limit: input validation. The model can't ask for 500 results; the SDK rejects it before our code runs. - ToolAnnotations(read_only_hint=True, open_world_hint=True): hints to the host that the tool doesn't change anything and talks to an external system. Hosts can use this to skip confirmation prompts for safe tools and ask before risky ones. - raise ToolError(...): turns our error into a tool result with isError: true. The model reads it and can recover. The server doesn't crash, and no stack trace leaks.

5. config.py: .env support

load_dotenv(override=False) reads GITHUB_TOKEN from a local .env file during development. override=False means a real environment variable (for example one set by Claude Desktop's config) wins. .env is in .gitignore, so the token never gets committed.

6. Tests: respx

respx intercepts httpx calls and returns fake responses, so the tests: - never touch the network (fast, no rate limits, work offline, work in CI), - can simulate failures that are hard to trigger for real: 404, timeouts.

The 5 tests cover: trimming works, a 404 becomes a readable tool error, the query and limit are passed correctly, the limit is validated, and a timeout becomes a tool error.

8. Interview questions for this step

  1. Why async? GitHub calls are I/O-bound; async lets one process serve concurrent requests while waiting on the network.
  2. Why one shared HTTP client instead of one per request? Connection pooling avoids repeated TCP/TLS handshakes; it also centralises config and is closed cleanly in the lifespan.
  3. What is the lifespan for? Startup/shutdown of shared resources and dependency injection into tools via the context.
  4. How does the model see errors? As tool results with isError: true and a human-readable message, so it can correct itself. Never crash, never leak stack traces or secrets.
  5. Why trim API responses? The context window is a budget; fewer, relevant fields mean cheaper calls and better model decisions.
  6. What makes a good tool description? Clear name, what it returns, when to use it vs other tools, parameter descriptions with examples, constraints in the schema.
  7. What are tool annotations? Hints like read-only/destructive/idempotent/open-world that hosts use for safety and UX decisions. They are hints, not security guarantees.
  8. How do you test code that calls an external API? Mock the HTTP layer (respx), test success and failure paths, keep live tests separate and optional.
  9. How do you handle the GitHub token? Env var / git-ignored .env, SecretStr so it never prints, fine-grained read-only scope, rotated by expiry.

Step 3 Reading code the model can explore a repository's folders and read its files, which is the core of "ask Claude about this codebase".

New tools: - list_directory(owner, repo, path="", ref=None) - get_file_contents(owner, repo, path, ref=None, max_chars=20000)

Changed files: server.py (two tools and shared parameter types), models.py (three new models), tests/test_contents.py (7 new tests, 13 in total).

1. The GitHub endpoint

Both tools use one endpoint: GET /repos/{owner}/{repo}/contents/{path}?ref=...

  • For a folder, it returns a JSON list of entries.
  • For a file, it returns a JSON object with the content base64-encoded.
  • ref selects a branch, tag or commit. When it's left out, you get the default branch.

So the code checks isinstance(data, list) to tell a folder from a file.

2. Why two tools instead of one get_contents?

We could expose the endpoint as a single tool, but two tools with clear names are easier for the model to use correctly: - The name says what you get back: a listing or text. - Each has its own output schema (DirectoryListing vs FileContents), so the result shape is predictable. - When the model calls the wrong one, the error tells it which tool to use instead ("'src' is a folder. Use list_directory..."). The model fixes its own mistake on the next call.

Interview line: "I designed tools around tasks the model does, not around API endpoints, and made error messages point to the right tool."

3. Guarding the context window

A repository can contain huge files. Pasting a 50,000-line file into the model's context is slow, expensive and pushes out more useful information. get_file_contents has three guards:

Case What happens Why
Long text file Cut off at max_chars (default 20,000, allowed range 1,000 to 100,000) and truncated: true Bounded cost; the flag tells the model it hasn't seen everything
Binary file (image, zip, compiled) is_binary: true, content: null Base64 or garbled bytes are useless to the model and waste tokens
File over 1 MB Clear tool error GitHub's contents API doesn't inline files over 1 MB (encoding: "none")

Binary detection (_decode_text): a file counts as text if it has no null bytes (\x00) and decodes as UTF-8. This is the same simple heuristic git and many editors use.

Why truncated matters: silently cutting text would let the model think it read the whole file and draw wrong conclusions. Being explicit about partial results is an important habit when building tools for LLMs.

4. Smaller details worth knowing

  • Folders first, then files, alphabetically (sorted(..., key=lambda e: (e["type"] != "dir", e["name"].lower()))). The key is a tuple: False sorts before True, so folders come first. This makes the listing easier for the model to scan, much like a file explorer.
  • quote(path) URL-encodes spaces and special characters but keeps /. Without it, a path like docs/my file.md would break the request.
  • Shared parameter types (Owner, Repo, Ref): defined once with their descriptions and reused by every tool. The model sees consistent descriptions everywhere, and we don't repeat ourselves (DRY).
  • Updated server instructions describe the workflow: list first, then read. Server instructions are a good place for guidance that spans several tools.

5. Tests (tests/test_contents.py)

Each guard has a test: 1. Folders sort before files. 2. list_directory on a file returns an error pointing to get_file_contents. 3. Text decodes correctly, and ref is passed to GitHub. 4. Long files are truncated and flagged. 5. Binary files return no content. 6. get_file_contents on a folder returns an error pointing to list_directory. 7. Files over 1 MB return a clear error.

7. Interview questions for this step

  1. How does your server stop a huge file from flooding the model's context? It truncates at a configurable max_chars with an explicit truncated flag, skips binary files, and rejects files over GitHub's 1 MB limit with a clear message.
  2. Why tell the model a result was truncated? So it knows it has partial information and can ask for more or say so to the user, instead of reasoning from an incomplete file as if it were complete.
  3. How do you detect binary files? Null bytes or invalid UTF-8 mean binary. It's a simple, widely used heuristic.
  4. Why two tools for one API endpoint? Task-oriented tools with clear names and typed outputs are easier for a model to pick and use; errors redirect it to the right tool.
  5. What is base64 and why does GitHub use it here? An encoding of arbitrary bytes into safe ASCII text so binary content can travel inside JSON.
  6. What's ref for? It lets the model read code at a specific branch, tag or commit, for example to compare a release with main or read the code a PR changes.

1. What pagination is and why it matters

APIs don't return thousands of items at once. They split results into pages. GitHub returns at most 100 items per page (per_page), and tells you where the next page is in a Link response header:

Link: <https://api.github.com/repos/o/r/issues?page=2&per_page=20>; rel="next",
      <https://api.github.com/repos/o/r/issues?page=9&per_page=20>; rel="last"

httpx parses this for us: response.links["next"]["url"].

Offset vs cursor pagination (a common interview question): - Offset/page-number (?page=3): simple and lets you jump to any page, but if items are added while you're paging, you can see duplicates or miss items. - Cursor (?after=abc123): the server gives an opaque pointer to "where you got to". Stable under changes and efficient for huge datasets, but you can only go forwards. - GitHub uses page numbers on most REST endpoints and cursors on some (and on GraphQL). By following the Link header instead of building URLs ourselves, our code works with either: we just follow whatever "next" GitHub gives us.

2. get_paginated in github_client.py

MAX_PAGES = 5


async def get_paginated(self, path, params=None, *, max_items, keep=lambda item: True):
    url = path
    query = {**(params or {}), "per_page": min(100, max(max_items, 1))}
    items = []

    for _ in range(MAX_PAGES):
        response = await self._get_response(url, query)
        items.extend(item for item in response.json() if keep(item))
        url = response.links.get("next", {}).get("url")
        if url is not None and not url.startswith(str(self._http.base_url).rstrip("/") + "/"):
            url = None
        query = None
        if url is None or len(items) >= max_items:
            break

    has_more = len(items) > max_items or url is not None
    return items[:max_items], has_more

Line by line: - MAX_PAGES = 5: a hard ceiling on requests per tool call. Even if the model asks for a lot, one call can never make more than 5 requests. This bounds latency, rate-limit usage and cost. - *,: everything after it must be passed by name (max_items=20), which makes calls self-explanatory. - keep: an optional filter function applied as items arrive. list_issues uses it to drop pull requests (see below). The default keeps everything. - per_page = min(100, max_items): ask for only as many as we need, up to GitHub's maximum of 100. Fewer, smaller requests. - for _ in range(MAX_PAGES): a bounded loop. while True with a "next" link could loop for a very long time on a huge repository. - response.links.get("next", {}).get("url"): the next page's URL, or None on the last page. - Same-host check: our client sends the token on every request. Following a "next" link to another host would leak it, so we only follow links that start with https://api.github.com/. The trailing / matters: without it, a look-alike host such as api.github.com.evil.example would pass. There's a test for exactly that case. - query = None: the "next" URL already includes every parameter, so we don't send them twice. - Stop early once we have enough items: no wasted requests. - has_more: true if we cut items off or GitHub still has a "next" page. The model is told the list is partial, the same principle as truncated in step 3. - items[:max_items]: never return more than asked.

get() and get_paginated() now share _get_response(), which holds the error handling in one place.

1. An error taxonomy: which failures are worth retrying?

Not every error deserves a retry. The key question is "would the exact same request succeed if I sent it again?"

Failure Example Retry? Why
Network / timeout Wi-Fi blip, ConnectTimeout Yes Usually temporary
Server error (5xx) 500, 502, 503, 504 Yes GitHub's problem, often gone in a second
Rate limit, short wait 429 with Retry-After: 2 Wait, then yes GitHub told us exactly when it's OK
Rate limit, long wait 403 with X-RateLimit-Remaining: 0, reset in 30 min No, report it Blocking a tool call for 30 minutes is worse than telling the user
Client error (other 4xx) 404 Not Found, 401, 422 No The same request will fail the same way; the model must change something

Idempotency is what makes retrying safe. A request is idempotent if doing it twice has the same effect as doing it once. Every call we make is a GET (read-only), so a retry can never, say, create two issues. When we add create_issue in step 6 (a POST), we must not blindly retry it: if the first attempt reached GitHub but the response was lost, a retry would create a duplicate.

2. Exponential backoff with jitter

MAX_ATTEMPTS = 3  # the first try plus two retries
BASE_DELAY_S = 0.5
...
delay = random.uniform(0, BASE_DELAY_S * 2 ** (attempt - 1))
  • Exponential: the maximum wait doubles each time (0.5 s, then 1 s). If GitHub is struggling, we back off instead of piling on.
  • Jitter (the randomness, random.uniform(0, ...)): if a thousand clients all failed at the same moment and all retried exactly 0.5 s later, they would hit GitHub together again (a "thundering herd"). Random waits spread them out. Picking anywhere from 0 to the ceiling is called full jitter.
  • Capped attempts: 3 attempts means the worst case is bounded (about 1.5 s of waiting plus the request timeouts). An LLM tool call must finish in reasonable time.

3. Rate limits

GitHub limits how many requests you can make:

  • Primary limit: 60 requests/hour without a token, 5,000 with one. Every response tells you where you stand in headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset (a Unix timestamp).
  • Secondary limits: protection against bursts (too many requests too fast, or too many searches). GitHub replies 403 or 429, usually with Retry-After: <seconds>.

_rate_limit_wait(response) works out how long GitHub wants us to wait, or None if the error isn't a rate limit:

if response.status_code not in (403, 429):
    return None
if retry_after header:                    → that many seconds  (secondary limit)
if X-RateLimit-Remaining == "0":          → reset time minus now  (hourly budget used up)
if status is 429 with no hint:            → 60 seconds  (GitHub's documented advice)
otherwise:                                → None  (a plain 403 is a permissions problem)

Then in _get_response:

  • Wait is 10 s or less (MAX_WAIT_S) → sleep that long and try again.
  • Wait is longer → stop and return a message: "GitHub rate limit reached. It resets in about 30 minute(s). Retrying now will not help; tell the user and try again later." Without a token it adds: "Adding a GITHUB_TOKEN raises the limit from 60 to 5,000 requests/hour."

Why tell the model "retrying now will not help"? Models tend to retry a failed tool. The error message is effectively a prompt: it tells the model what to do next (stop and inform the user). The server instructions say the same and point to get_rate_limit.

Why is a 403 not always a rate limit? GitHub uses 403 for both "you've used your quota" and "you don't have permission". The headers tell them apart. Treating a permissions 403 as a rate limit would make us wait for nothing; a test checks we don't.

4. The retry loop in _get_response, line by line

for attempt in range(1, MAX_ATTEMPTS + 1):
    try:
        response = await self._http.get(url, params=params)
    except httpx.TimeoutException as exc:
        error = GitHubAPIError(504, f"GitHub did not respond in time ({url}).")
        error.__cause__ = exc
    except httpx.HTTPError as exc:
        error = GitHubAPIError(502, f"Could not reach GitHub: {exc}")
        error.__cause__ = exc
    else:
        if response.is_success:
            return response

        wait = _rate_limit_wait(response)
        if wait is not None:
            if wait > MAX_WAIT_S or attempt == MAX_ATTEMPTS:
                raise GitHubAPIError(response.status_code, self._rate_limit_message(wait))
            await _sleep(wait)
            continue

        error = GitHubAPIError(response.status_code, _error_message(response))
        if response.status_code not in RETRYABLE_STATUS:
            raise error

    if attempt == MAX_ATTEMPTS:
        raise GitHubAPIError(
            error.status_code, f"{error} Gave up after {MAX_ATTEMPTS} attempts."
        ) from error.__cause__

    delay = random.uniform(0, BASE_DELAY_S * 2 ** (attempt - 1))
    logger.warning(...)
    await _sleep(delay)
  • try / except / else: the else block runs only if no exception happened, i.e. we got a response. Network failures are handled in the except blocks.
  • error.__cause__ = exc: keeps the original exception attached, the same as raise ... from exc, so a developer reading a traceback sees the real cause.
  • continue after a rate-limit wait skips the backoff and goes straight to the next attempt.
  • Non-retryable 4xx → raise error immediately: no wasted requests.
  • "Gave up after 3 attempts": tells the model the server already retried, so retrying again itself is pointless.
  • logger.warning goes to stderr, so retries are visible in the Inspector's server log without breaking the stdio protocol.
  • _sleep is a module-level alias for asyncio.sleep. Tests replace it so they never really wait (see below). asyncio.sleep (not time.sleep) lets the server keep serving other requests while it waits.

  1. Which errors do you retry, and which not? Timeouts, network errors and 5xx, because they're usually temporary. Not other 4xx, because the same request fails the same way; the model has to change its input instead.

  • ResourceError: resources have no isError result like tools do, so the error goes back as a protocol error with our readable message.

  • Prompts can do work too. This one fetches the PR's title, author, branches, description and the diff of every changed file, so the model starts the review with everything in front of it instead of making several tool calls first.

CREATES_DATA = ToolAnnotations(
    read_only_hint=False, destructive_hint=False, idempotent_hint=False, open_world_hint=True

@mcp.tool(annotations=CREATES_DATA)
async def create_issue(
    owner: Owner,
    repo: Repo,
    title: Annotated[str, Field(min_length=1, max_length=256, description="Issue title")],
    ctx: Context,
    body: Annotated[str | None, Field(description="Issue description in Markdown")] = None,
    labels: Annotated[list[str] | None, Field(description="Existing label names ...")] = None,
) -> CreatedIssue:
    """Create a new issue ... Only use it when the user asked for an issue;
    confirm the title and body with them first."""
    if not settings.allow_writes:
        raise ToolError(
            "Creating issues is turned off on this server. To allow it, set "
            "GITHUB_ALLOW_WRITES=true and use a token with Issues write permission."
        )
    payload = {"title": title}  # plus body and labels when given
    data = await _github(ctx).post(f"/repos/{owner}/{repo}/issues", json=payload)
    return CreatedIssue.from_api(data, repository=f"{owner}/{repo}")

Five layers of protection, from the outside in:

  1. Least-privilege token. Your token is read-only, so even if everything else failed, GitHub itself would refuse (403). To really create issues you'd make a separate token with Issues: Read and write on chosen repositories only.
  2. Off by default (GITHUB_ALLOW_WRITES). A server that can write should need a deliberate opt-in. server_status now reports writes_enabled.
  3. Tool annotations. read_only_hint=False tells the host this tool changes things, so hosts like Claude Desktop ask the user to approve each call (human in the loop). destructive_hint=False: it only adds, never deletes or overwrites. idempotent_hint=False: calling it twice makes two issues. Annotations are hints, not security: a host may ignore them, which is why layers 1 and 2 exist.
  4. Instructions in the docstring and server instructions: only create an issue when the user asked, and show them the title and body first. That's the prompt telling the model how to behave.
  5. No blind retries (next section).

Plus input validation: title must be 1 to 256 characters (min_length, max_length become JSON Schema rules), so an empty title is rejected before any request.

5. Why POST is never retried after a 5xx or timeout

In step 5 we retried timeouts and 5xx because GET is idempotent. A POST isn't: if GitHub created the issue but the response was lost (timeout) or a proxy returned 502 afterwards, a retry would create a duplicate issue. So the retry loop, now _request(method, url, *, params=None, json=None), checks:

idempotent = method == "GET"
...
if not idempotent:
    raise GitHubAPIError(
        error.status_code,
        f"{error} The {method} was not retried because it may already have "
        "succeeded. Check before trying again.",
    ) from error.__cause__

The message tells the model to check first (for example with list_issues) before trying again. Rate-limit waits still apply to POST: a 429 means GitHub rejected the request, so nothing was created and repeating is safe.

Also new in github_client.py: self._http.request(method, url, params=..., json=...) replaces self._http.get(...), and json= makes httpx send a JSON body with the right Content-Type.

Interview line: "Retries are only safe for idempotent requests. For non-idempotent writes, you either use an idempotency key (if the API supports one, like Stripe does) or you don't retry and let the caller check. GitHub's issues API has no idempotency key, so I don't retry."

8. Interview questions for this step

  1. What's the difference between tools, resources and prompts? Tools are actions the model chooses to call and may have side effects. Resources are read-only data with URIs that the application or user attaches. Prompts are templates the user picks, like slash commands.
  2. How do you make a write tool safe? Least-privilege token, off by default behind a setting, tool annotations so hosts ask the user to approve, instructions to confirm with the user first, input validation, and no blind retries.
  3. Are tool annotations a security boundary? No, they're hints a host may ignore. Real enforcement is the token's permissions and the server-side switch.
  4. Why not retry a failed POST? It's not idempotent: the first attempt may have succeeded before the error, so a retry could create a duplicate. Without an idempotency key, I report the failure and tell the model to check first.
  5. Why does review_pull_request load the diff itself instead of letting the model call tools? It saves several round-trips and gives the model the full context up front, with a size budget so a huge PR can't flood the context.
  6. What's a resource template? A resource URI with placeholders (RFC 6570), like github://repos/{owner}/{repo}/readme, so one definition serves every repository.

Continuous integration means every change is automatically built and tested on a clean machine, not just on your laptop. It catches:

1. stdio vs Streamable HTTP

MCP defines how messages (JSON-RPC) travel between client and server. That's the transport. There are two that matter:

stdio Streamable HTTP
Who starts the server The client starts it as a child process It runs on its own, as a service
How they talk stdin / stdout HTTP POST to one endpoint (/mcp)
How many clients Exactly one Many, possibly on other machines
Security Nothing listens on the network Anyone who can reach the port can call it
Typical use Claude Desktop, Claude Code on your laptop A shared team server, a container, the cloud

Until now we only had stdio. It's the right default (simplest, safest), so it stays the default. HTTP is opt-in: MCP_TRANSPORT=http.

The key insight: the tools, resources and prompts don't change at all. Only the way bytes arrive changes. That's why server.py needed just a few lines: the transport is a separate layer, which is exactly the point of MCP's design.

def main() -> None:
    logger.info("Starting GitHub MCP server v%s (%s)", __version__, settings.transport)
    if settings.transport == "http":
        from github_mcp.http_app import serve

        serve(settings)
    else:
        mcp.run()  # stdio: the client starts this process and talks over stdin/stdout

The import is inside the if so stdio users never load the web server code.

2. The new problem: the network

With stdio, only the program that started the server can talk to it. With HTTP, anyone who can reach the port can, and every request uses your GitHub token. So http_app.py adds three guards.

Guard 1: loopback by default

MCP_HOST defaults to 127.0.0.1 (loopback: only programs on the same computer can connect). 0.0.0.0 means "every network interface", which is what a container needs (see below) but is dangerous on a laptop on public Wi-Fi.

Guard 2: a bearer token, required off loopback

if settings.http_host not in LOOPBACK_HOSTS and settings.auth_token is None:
    raise RuntimeError(f"Refusing to listen on {settings.http_host} without MCP_AUTH_TOKEN: ...")
  • Fail closed: an unsafe configuration doesn't start with a warning nobody reads, it refuses to start, with a message saying how to fix it. The same philosophy as writes being off by default.
  • Clients send Authorization: Bearer <token>. A bearer token means "whoever bears (holds) this token is allowed in", like a ticket.

The check is a small ASGI middleware. ASGI is the standard interface between Python web servers (uvicorn) and web apps (Starlette): an app is just async def app(scope, receive, send). A middleware is an app that wraps another app and decides whether to pass the request on:

async def __call__(self, scope, receive, send):
    if scope["type"] != "http" or scope["path"] in PUBLIC_PATHS:
        await self.app(scope, receive, send)        # lifespan events and /health pass
        return
    supplied = dict(scope["headers"]).get(b"authorization", b"")
    if hmac.compare_digest(supplied, self._expected):
        await self.app(scope, receive, send)        # right token: through
        return
    ...send a 401 with "WWW-Authenticate: Bearer"
  • hmac.compare_digest, not ==: == stops at the first different character, so a wrong guess that starts correctly takes slightly longer. Measured over many requests, that leaks the token one character at a time (a timing attack). compare_digest always takes the same time.
  • 401 Unauthorized with WWW-Authenticate: Bearer is the standard HTTP way to say "you need a bearer token".
  • Why not OAuth? The SDK supports full OAuth 2.1, which is the right choice for a public multi-user service (each user logs in, gets their own scopes). For a single-owner server, a shared secret is simpler and adequate. Knowing when each is appropriate is the interview point.

Guard 3: DNS rebinding protection

A subtle browser attack: you visit evil.example. Its page makes your browser send requests to evil.example, then the attacker changes the DNS record of evil.example to point to 127.0.0.1. Your browser now sends requests to your local server, but still with Host: evil.example. The defence is to refuse any request whose Host header isn't one we expect:

security = TransportSecuritySettings(
    enable_dns_rebinding_protection=True,
    allowed_hosts=["127.0.0.1:*", "localhost:*", "[::1]:*"] + settings.allowed_hosts,
    ...
)

The SDK enables this automatically only when the host is loopback; in a container the host is 0.0.0.0, so we turn it on explicitly. A refused request gets 421 Misdirected Request. MCP_ALLOWED_HOSTS adds names when you deploy behind a real domain.

Stateless and JSON

app = mcp.streamable_http_app(stateless_http=True, json_response=True, ...)
  • Stateless: each request stands alone; the server keeps no session between requests. Any copy of the server can answer any request, so you can run several behind a load balancer, and a restart loses nothing. We can do this because our server has no per-session state (no subscriptions, no server-to-client requests).
  • JSON responses: Streamable HTTP can answer with a stream of events (SSE) for long-running work with progress updates. Our tools answer in one go, so plain JSON is simpler to call and to debug with curl.
  • The GitHub client is still created once at startup: the SDK's session manager enters our lifespan once, not per request.

/health

@mcp.custom_route("/health", methods=["GET"])
async def health(_request: Request) -> JSONResponse:
    return JSONResponse({"status": "ok", "version": __version__})

A liveness check: Docker, Kubernetes and load balancers poll it to know the process is alive. It needs no token (it reveals nothing) and calls nothing (it must be cheap and must not use the GitHub rate limit).

Core concepts

What MCP is and why it exists

Before MCP, every AI app needed its own custom integration for every service: N apps × M services = N×M integrations. MCP (Model Context Protocol) is an open standard, created by Anthropic, that turns this into N + M: each service is wrapped once as an MCP server, and every MCP-compatible app can use it. It's often described as "USB-C for AI tools".

The three roles

Role What it is In this project
Host The AI application the user talks to Claude Desktop, Claude Code, the MCP Inspector
Client A component inside the host holding one connection to one server Built into the host; in tests, mcp.Client
Server A program exposing capabilities and doing the work Our github-mcp server

The three server primitives

Primitive Who controls it Example
Tool The model decides to call it search_repositories
Resource The application/user attaches it as read-only context, addressed by a URI github://repos/{owner}/{repo}/readme
Prompt The user picks it, like a slash command review_pull_request, summarize_repository

This is one of the most common MCP interview questions. Memorise: model-controlled, application-controlled, user-controlled.

How a session works

All messages are JSON-RPC 2.0: requests with an id, method and params, and responses with a result or error.

  1. The host starts our server as a subprocess.
  2. initialize: client and server exchange protocol version and capabilities; the server sends its instructions.
  3. tools/list: the server returns every tool's name, description and input/output JSON Schema.
  4. The user asks something. The model reads the tool list and decides to call one.
  5. tools/call: the host sends the tool name and arguments; our function runs and returns a result (or an error result).
  6. The model reads the result and either answers or calls another tool.

Transports

  • stdio (what we use): the host launches the server and talks over stdin/stdout. It's local, simple, and nothing listens on the network, so the token never leaves the machine. Consequence: stdout belongs to the protocol. Any print() corrupts the stream, which is why we log to stderr.
  • Streamable HTTP (step 8, MCP_TRANSPORT=http): the server runs as a web service; clients POST JSON-RPC to one endpoint, /mcp. Good for containers, shared or remote servers. Because anyone who can reach the port could use the token, it needs protection: we listen on loopback by default, require a bearer token anywhere else, and check the Host header (DNS rebinding protection). Public multi-user services would use OAuth 2.1.
  • The tools don't change between transports. Only how bytes arrive changes, which is why adding HTTP took one new module and a few lines in main().

4.2 config.py: settings

import os

from dotenv import load_dotenv
from pydantic import BaseModel, Field, SecretStr


class Settings(BaseModel):
    github_token: SecretStr | None = None
    github_api_url: str = "https://api.github.com"
    request_timeout_s: float = Field(default=15.0, gt=0)
    # Write tools (create_issue) refuse to run unless this is switched on explicitly.
    allow_writes: bool = False

    @classmethod
    def from_env(cls) -> "Settings":
        # Real environment variables win over .env (override=False).
        load_dotenv(override=False)
        return cls(
            github_token=os.environ.get("GITHUB_TOKEN") or None,
            github_api_url=os.environ.get("GITHUB_API_URL", "https://api.github.com"),
            request_timeout_s=float(os.environ.get("GITHUB_TIMEOUT_S", "15")),
            allow_writes=os.environ.get("GITHUB_ALLOW_WRITES", "").lower() in {"1", "true", "yes"},
        )
  • class Settings(BaseModel): a Pydantic model, so every value is type-checked when the server starts. Bad config fails immediately and clearly instead of halfway through a request.
  • SecretStr: wraps the token so that printing or logging it shows **********. The real value is only read with .get_secret_value(), in exactly one place (the HTTP client).
  • | None = None: the token is optional. Without one, GitHub still works but allows only 60 requests/hour instead of 5,000.
  • Field(default=15.0, gt=0): the timeout must be greater than 0. Pydantic enforces this.
  • @classmethod from_env: a constructor that builds Settings from the environment. Keeping this in one place means the rest of the code never touches os.environ.

  • os.environ.get("GITHUB_TOKEN") or None: turns an empty string into None, so an empty GITHUB_TOKEN= line counts as "no token".
  • allow_writes (step 6): False unless GITHUB_ALLOW_WRITES is 1, true or yes. A server that can change things should need a deliberate opt-in; anything else (unset, a typo) means off.

Why environment variables? That's how MCP hosts pass secrets to servers (env in the host config). Never hard-code a token and never commit .env.

4.3 github_client.py: the HTTP layer

The error type

class GitHubAPIError(Exception):
    """A GitHub API call failed. The message is written to be read by the model."""

    def __init__(self, status_code: int, message: str):
        super().__init__(message)
        self.status_code = status_code
  • A custom exception means callers only need to catch one type for every GitHub failure (network, timeout, 404, 401…).
  • It keeps the status_code so code can react differently later (step 5 uses it to decide what to retry).
  • The message is written for the model to read, because the model decides what to do next.

Creating the client

class GitHubClient:
    def __init__(self, settings: Settings):
        headers = {
            "Accept": "application/vnd.github+json",
            "X-GitHub-Api-Version": "2022-11-28",
            "User-Agent": f"github-mcp-server/{__version__}",
        }
        if settings.github_token is not None:
            headers["Authorization"] = f"Bearer {settings.github_token.get_secret_value()}"

        self._http = httpx.AsyncClient(
            base_url=settings.github_api_url,
            headers=headers,
            timeout=settings.request_timeout_s,
        )
        self._authenticated = settings.github_token is not None  # step 5: for error hints
  • Accept: application/vnd.github+json: GitHub's recommended media type for its REST API.
  • X-GitHub-Api-Version: 2022-11-28: pins the API version, so a future GitHub change can't silently alter responses.
  • User-Agent: GitHub rejects requests without one. Including the version helps GitHub (and you) identify traffic.
  • Authorization: Bearer ...: added only when a token exists. This is the one place the secret is unwrapped.
  • httpx.AsyncClient(...): created once and reused for every call:
    • It keeps a connection pool: the TCP + TLS handshake (often 100ms+) happens once, not per request.
    • base_url means calls only pass the path (/repos/...).
    • timeout makes sure a hung network call can't hang the model forever.
  • self._http: the leading underscore marks it private. Only this class touches HTTP.

Making a request

async def get(self, path: str, params: dict[str, Any] | None = None) -> Any:
    response = await self._request("GET", path, params=params)
    return response.json()


async def post(self, path: str, json: dict[str, Any]) -> Any:
    """Send a POST (it creates something on GitHub). Never retried after a network
    error or 5xx, because the first attempt may already have succeeded."""
    response = await self._request("POST", path, json=json)
    return response.json()


async def aclose(self) -> None:
    await self._http.aclose()
  • get() is for single objects (one repository, one file). It returns parsed JSON.
  • post() (step 6) sends a JSON body to create something. Only create_issue uses it.
  • _request() does the actual request, the retries and all the error handling, and returns the full response (so pagination can read its headers). get(), post() and get_paginated() all use it, so error handling lives in exactly one place. It is explained in full in Retries and rate limits (step 5) below.
  • async def / await: while waiting for GitHub, Python can serve other requests. Network calls are I/O-bound (mostly waiting), which is exactly where async helps.
  • params=params: httpx turns a dict like {"q": "mcp", "per_page": 5} into ?q=mcp&per_page=5, URL-encoding it safely.
  • aclose(): closes the pooled connections. The server calls it at shutdown.

Pagination (step 4)

GitHub never returns a long list in one go. It returns pages (at most 100 items each) and puts the address of the next page in a Link header:

Link: <https://api.github.com/repos/o/r/issues?page=2&per_page=20>; rel="next"
# Hard stop on how many pages one tool call may fetch, whatever the model asks for.
MAX_PAGES = 5

    async def get_paginated(
        self,
        path: str,
        params: dict[str, Any] | None = None,
        *,
        max_items: int,
        keep: Callable[[dict[str, Any]], bool] = lambda item: True,
    ) -> tuple[list[dict[str, Any]], bool]:
        url: str | None = path
        query = {**(params or {}), "per_page": min(100, max(max_items, 1))}
        items: list[dict[str, Any]] = []

        for _ in range(MAX_PAGES):
            response = await self._request("GET", url, params=query)
            items.extend(item for item in response.json() if keep(item))
            url = response.links.get("next", {}).get("url")
            # Our token is sent with every request, so only follow links back to GitHub.
            if url is not None and not url.startswith(str(self._http.base_url).rstrip("/") + "/"):
                url = None
            # The "next" URL already carries every query parameter.
            query = None
            if url is None or len(items) >= max_items:
                break

        has_more = len(items) > max_items or url is not None
        return items[:max_items], has_more
  • MAX_PAGES = 5: a hard ceiling. Whatever the model asks for, one tool call makes at most 5 requests. This bounds time, rate-limit use and context size.
  • *, in the signature: everything after it must be passed by name (max_items=20), so calls read clearly.
  • keep: an optional filter applied as items arrive. The default lambda item: True keeps everything; list_issues passes one that drops pull requests.
  • -> tuple[list[...], bool]: returns two things, the items and whether more exist.
  • {**(params or {}), "per_page": ...}: copies the caller's parameters and adds the page size. min(100, ...) respects GitHub's maximum; asking only for what we need avoids wasted data.
  • for _ in range(MAX_PAGES): a bounded loop. while True could run for a very long time on a big repository. _ means "I don't need the counter".
  • items.extend(item for item in ... if keep(item)): adds this page's items, filtered.
  • response.links: httpx parses the Link header into a dict for us. .get("next", {}).get("url") gives the next URL, or None on the last page.
  • Same-host check (security): the client sends the token on every request. If a "next" URL ever pointed to another host, following it would leak the token. We only follow URLs starting with https://api.github.com/. The trailing / matters: without it, a look-alike host like api.github.com.evil.example would pass. A test checks exactly this.
  • query = None: the next URL already contains all parameters; sending them again would duplicate them.
  • Stop early once we have enough items.
  • has_more: true if we cut items off or GitHub still had a next page. The model is told the list is partial, the same idea as truncated in step 3.
  • items[:max_items]: never return more than asked.

Why follow Link instead of building ?page=N ourselves? GitHub uses page numbers on most endpoints but cursors on some. Following whatever "next" link GitHub gives works with both, and if GitHub changes its scheme our code keeps working.

Retries and rate limits (step 5)

New constants at the top of the file:

MAX_ATTEMPTS = 3  # the first try plus two retries
BASE_DELAY_S = 0.5  # backoff ceiling doubles each time: 0.5s, then 1s
RETRYABLE_STATUS = {500, 502, 503, 504}

# A tool call should never hang for minutes. Longer rate-limit waits are reported instead.
MAX_WAIT_S = 10.0

logger = logging.getLogger("github_mcp.github_client")

# Indirection so tests can replace sleeping with a recorder and run instantly.
_sleep = asyncio.sleep

The error taxonomy. The question behind every decision is "would the exact same request succeed if sent again?"

Failure Retry? Why
Timeout or network error Yes (GET only) Usually temporary
500, 502, 503, 504 Yes (GET only) GitHub's problem, often gone in a second
Rate limit with a short wait (≤ 10 s) Wait, then yes GitHub said when it's OK
Rate limit with a long wait No, report it A tool call must not hang for 30 minutes
Other 4xx (404, 401, 422, plain 403) No Same request, same failure; the model must change its input

Idempotency makes retrying safe: every read here is a GET, and doing a GET twice changes nothing. A POST such as create_issue must not be retried blindly, because a lost response could mean the issue was created and a retry would make a duplicate. Since step 6 the loop enforces this (see below). Some APIs (Stripe, for example) accept an idempotency key that makes retried POSTs safe; GitHub's issues API doesn't.

async def _request(
    self,
    method: str,
    url: str,
    *,
    params: dict[str, Any] | None = None,
    json: dict[str, Any] | None = None,
) -> httpx.Response:
    idempotent = method == "GET"
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            response = await self._http.request(method, url, params=params, json=json)
        except httpx.TimeoutException as exc:
            error = GitHubAPIError(504, f"GitHub did not respond in time ({url}).")
            error.__cause__ = exc
        except httpx.HTTPError as exc:
            error = GitHubAPIError(502, f"Could not reach GitHub: {exc}")
            error.__cause__ = exc
        else:
            if response.is_success:
                return response

            wait = _rate_limit_wait(response)
            if wait is not None:
                if wait > MAX_WAIT_S or attempt == MAX_ATTEMPTS:
                    raise GitHubAPIError(response.status_code, self._rate_limit_message(wait))
                logger.warning("Rate limited by GitHub; waiting %.1fs before retrying", wait)
                await _sleep(wait)
                continue

            error = GitHubAPIError(response.status_code, _error_message(response))
            if response.status_code not in RETRYABLE_STATUS:
                raise error

        if not idempotent:
            # The request may have reached GitHub before the failure; a repeat could
            # create a duplicate. Let the caller (the model) check and decide.
            raise GitHubAPIError(
                error.status_code,
                f"{error} The {method} was not retried because it may already have "
                "succeeded. Check before trying again.",
            ) from error.__cause__

        if attempt == MAX_ATTEMPTS:
            raise GitHubAPIError(
                error.status_code, f"{error} Gave up after {MAX_ATTEMPTS} attempts."
            ) from error.__cause__

        delay = random.uniform(0, BASE_DELAY_S * 2 ** (attempt - 1))
        logger.warning("Attempt %d failed (%s); retrying in %.2fs", attempt, error, delay)
        await _sleep(delay)

    raise AssertionError("unreachable")  # the loop always returns or raises
  • method, json (step 6): one loop serves GET and POST. self._http.request(method, ...) sends either; json= makes httpx send a JSON body with the right Content-Type.
  • idempotent = method == "GET": only GETs may be repeated after a timeout or 5xx.
  • for attempt in range(1, MAX_ATTEMPTS + 1): a bounded loop, attempts 1, 2 and 3.
  • try / except / else: except handles "no response at all" (network, timeout); else runs only when a response arrived.
  • Order of except matters: TimeoutException is a kind of HTTPError, so it must be caught first to get the more specific message.
  • 504 / 502: standard HTTP gateway codes reused for "GitHub timed out" and "GitHub unreachable".
  • error.__cause__ = exc: attaches the original exception, the same thing raise ... from exc does, so tracebacks show the real cause.
  • response.is_success: true for any 2xx status; return straight away.
  • Rate limit branch: a short wait is slept out and the loop continues to the next attempt; a long wait (or no attempts left) raises a message with the reset time instead.
  • if response.status_code not in RETRYABLE_STATUS: raise error: other 4xx errors fail immediately. No wasted requests.
  • if not idempotent: raise ... (step 6): a POST that hit a timeout or 5xx is not retried, because GitHub may have created the issue before the error and a retry would make a duplicate. The message tells the model to check first (e.g. with list_issues). Rate-limit waits still apply to POST: a 429 means GitHub rejected it, so nothing was created.
  • "Gave up after 3 attempts": tells the model the server already retried, so retrying again itself is pointless.
  • random.uniform(0, 0.5 * 2 ** (attempt - 1)): exponential backoff with full jitter. The ceiling doubles (0.5 s, 1 s) so a struggling GitHub isn't hammered; the random pick spreads out many clients that failed at the same time (avoiding a "thundering herd").
  • logger.warning: goes to stderr, so retries show in the Inspector's server log without breaking stdio.
  • await _sleep(...): asyncio.sleep, not time.sleep, so the server keeps serving other requests while waiting. Tests swap _sleep for a recorder.
  • raise AssertionError("unreachable"): the loop always returns or raises; this line satisfies type checkers and would flag a logic bug loudly.

How long does GitHub want us to wait?

def _rate_limit_wait(response: httpx.Response) -> float | None:
    """Seconds GitHub wants us to wait, or None if this error is not a rate limit."""
    if response.status_code not in (403, 429):
        return None
    retry_after = response.headers.get("retry-after")
    if retry_after is not None:  # secondary rate limit: GitHub says exactly how long
        try:
            return max(0.0, float(retry_after))
        except ValueError:
            return 60.0
    if response.headers.get("x-ratelimit-remaining") == "0":  # hourly budget used up
        try:
            return max(0.0, int(response.headers["x-ratelimit-reset"]) - time.time())
        except (KeyError, ValueError):
            return 60.0
    if response.status_code == 429:  # no hint given; GitHub's docs say wait a minute
        return 60.0
    return None  # a 403 without rate-limit headers is a permissions problem
  • Primary limit: 60 requests/hour without a token, 5,000 with one. Every response carries X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset (a Unix timestamp).
  • Secondary limits: burst protection (too many requests too fast). GitHub answers 403 or 429, usually with Retry-After: <seconds>.
  • 403 is ambiguous: GitHub uses it for both "quota used up" and "no permission". The headers tell them apart; a plain 403 returns None so we don't wait for nothing.
  • max(0.0, ...): never a negative wait if the clock says the reset already passed.
  • Fallback of 60 seconds when a header is malformed, following GitHub's guidance.
def _rate_limit_message(self, wait_s: float) -> str:
    minutes = max(1, round(wait_s / 60))
    message = (
        f"GitHub rate limit reached. It resets in about {minutes} minute(s). "
        "Retrying now will not help; tell the user and try again later."
    )
    if not self._authenticated:
        message += " Adding a GITHUB_TOKEN raises the limit from 60 to 5,000 requests/hour."
    return message
  • The error message is a prompt. Models tend to retry failed tools, so the message says plainly what to do instead: stop and tell the user.
  • self._authenticated is set in __init__ from settings.github_token is not None; the token hint only appears when it would actually help.

@dataclass

    github: GitHubClient


@asynccontextmanager

async def _get_contents(ctx: Context, owner: str, repo: str, path: str, ref: str | None):
    # quote() escapes spaces and special characters but keeps "/" between folders.
    path = path.strip("/")
    url = f"/repos/{owner}/{repo}/contents" + (f"/{quote(path)}" if path else "")
    params = {"ref": ref} if ref else None

    except GitHubAPIError as exc:
        raise ToolError(str(exc)) from exc

  • quote(path): URL-encodes spaces and special characters (my file.md → my%20file.md) but keeps /.

  • ref (branch, tag or commit) is only sent when given; otherwise GitHub uses the default branch.

@mcp.tool(annotations=READ_ONLY)
async def list_directory(
    owner: Owner,
    repo: Repo,
    ctx: Context,
    path: Annotated[str, Field(description="Folder path; empty for the repository root")] = "",
    ref: Ref = None,

    structure of a codebase before reading individual files with get_file_contents."""
    data = await _get_contents(ctx, owner, repo, path, ref)
    if not isinstance(data, list):
        raise ToolError(f"'{path}' is a file, not a folder. Use get_file_contents to read it.")

    # Folders first, then files, each alphabetically: easier for the model to scan.
    entries = sorted(data, key=lambda e: (e["type"] != "dir", e["name"].lower()))
    return DirectoryListing(
        repository=f"{owner}/{repo}",
        path=path.strip("/") or "/",
        entries=[
            DirectoryEntry(name=e["name"], path=e["path"], type=e["type"], size=e["size"])
            for e in entries
        ],
    )
  • isinstance(data, list): tells a folder (list) from a file (object).

  • Sorting with a tuple key (e["type"] != "dir", e["name"].lower()):
    • Python sorts tuples element by element.
    • e["type"] != "dir" is False for folders and True for files, and False < True, so folders come first.
    • .lower() makes the alphabetical order case-insensitive.

@mcp.tool(annotations=READ_ONLY)
async def get_file_contents(
    owner: Owner,
    repo: Repo,
    path: Annotated[
        str, Field(description="File path from the repository root, e.g. 'src/app.py'")
    ],
    ctx: Context,
    ref: Ref = None,
    max_chars: Annotated[
        int,
        Field(ge=1_000, le=100_000, description="Cut the file off after this many characters"),
    ] = 20_000,
) -> FileContents:
    """Read the text of one file in a repository. Long files are cut off at max_chars
    (truncated=true tells you this happened). Binary files return no content."""
    data = await _get_contents(ctx, owner, repo, path, ref)
    if isinstance(data, list):
        raise ToolError(f"'{path}' is a folder. Use list_directory to see what's inside.")
    if data.get("type") != "file":
        raise ToolError(f"'{path}' is a {data.get('type')}, not a regular file.")
  • max_chars between 1,000 and 100,000, default 20,000: the model can ask for more when needed, but never unlimited. 20_000 is just 20000 with an underscore for readability.
  • The docstring explains the flags, so the model knows what truncated and binary mean.
  • Two guard clauses: a folder → redirect to list_directory; a symlink or submodule → clear error.
    result = FileContents(
        repository=f"{owner}/{repo}",
        path=data["path"],
        size=data["size"],
        is_binary=False,
        truncated=False,
        content=None,
    )

    # GitHub only inlines files up to 1 MB; bigger ones come back with encoding "none".
    if data.get("encoding") != "base64":
        raise ToolError(
            f"'{path}' is {data['size']:,} bytes, too large to read through the GitHub API "
            "(1 MB limit)."
        )

    raw = base64.b64decode(data["content"])
    text = _decode_text(raw)
    if text is None:
        result.is_binary = True
        return result

    result.truncated = len(text) > max_chars
    result.content = text[:max_chars]
    return result
  • Start with safe defaults, then fill in. Every return path gives a complete, valid result.
  • Files over 1 MB: GitHub's contents API doesn't include their content (encoding: "none"), so we explain this instead of returning nothing. {:,} formats 5000000 as 5,000,000.
  • base64.b64decode: GitHub sends file bytes as base64 text inside JSON. We decode them back to raw bytes.
  • Binary files return is_binary: true and no content, since base64 or garbled bytes waste tokens and are useless to the model.
  • result.truncated = len(text) > max_chars: an explicit flag. Silently cutting text would let the model think it saw the whole file.
  • text[:max_chars]: Python slicing; it's safe even when the text is shorter.
def _decode_text(raw: bytes) -> str | None:
    """Return the bytes as UTF-8 text, or None if they look like a binary file."""
    if b"\x00" in raw:  # text files practically never contain null bytes
        return None
    try:
        return raw.decode("utf-8")
    except UnicodeDecodeError:
        return None
  • Binary detection heuristic: a null byte (\x00), or bytes that aren't valid UTF-8, means binary. Git uses the same idea.
  • Returning None (instead of raising) keeps the caller simple: if text is None.

    )

    if body:
        payload["body"] = body
    if labels:
        payload["labels"] = labels
    try:
        data = await _github(ctx).post(f"/repos/{owner}/{repo}/issues", json=payload)
    except GitHubAPIError as exc:
        raise ToolError(str(exc)) from exc
    logger.info("Created issue %s/%s#%s", owner, repo, data.get("number"))
    return CreatedIssue.from_api(data, repository=f"{owner}/{repo}")

Five layers of safety, outermost first:

  1. Least-privilege token: yours is read-only, so GitHub itself would refuse a write (403). Writing needs a separate token with Issues: Read and write on chosen repositories.
  2. Off by default: settings.allow_writes must be switched on with GITHUB_ALLOW_WRITES=true. The check runs before any request.
  3. Annotations: read_only_hint=False (it changes things), destructive_hint=False (it only adds, never deletes or overwrites), idempotent_hint=False (two calls make two issues). Hosts like Claude Desktop use this to ask the user to approve each call: human in the loop. Annotations are hints, not security, which is why layers 1 and 2 exist.
  4. Docstring and server instructions: only when the user asked, and confirm the title and body first.
  5. No blind retries: post() never retries after a timeout or 5xx (see Retries and rate limits).

Details:

  • Field(min_length=1, max_length=256) becomes JSON Schema rules, so an empty title is rejected before our code runs.
  • Only send what was given: body and labels are added to the payload only when present.
  • logger.info: writes are worth a log line (an audit trail), on stderr as always.

MAX_DIFF_CHARS = 40_000


@mcp.prompt(title="Review a pull request")
async def review_pull_request(owner: str, repo: str, number: int, ctx: Context) -> str:
    """Review a pull request. The PR's description and changed lines are loaded for you."""
    github = _github(ctx)
    try:
        pr = await github.get(f"/repos/{owner}/{repo}/pulls/{number}")
        files, more_files = await github.get_paginated(
            f"/repos/{owner}/{repo}/pulls/{number}/files", max_items=100
        )
    except GitHubAPIError as exc:
        code = INVALID_PARAMS if exc.status_code < 500 else INTERNAL_ERROR
        raise MCPError(code, str(exc)) from exc

    author = (pr.get("user") or {}).get("login")
    intro = (
        f'Please review pull request #{number} in {owner}/{repo}: "{pr["title"]}" by '
        f"{author}, merging {pr['head']['ref']} into {pr['base']['ref']}."
    )
    parts = [
        intro,
        f"Description:\n{pr.get('body') or '(no description)'}",
        f"Changed files ({len(files)}{'+' if more_files else ''}):",
    ]
    budget = MAX_DIFF_CHARS
    skipped = 0
    for f in files:
        header = f"### {f['filename']} ({f['status']}, +{f['additions']} -{f['deletions']})"
        patch = f.get("patch") or "(no text diff: binary or very large file)"
        if len(patch) > budget:
            skipped += 1
            parts.append(f"{header}\n(diff left out to keep this prompt short)")
            continue
        budget -= len(patch)
        parts.append(f"{header}\n```diff\n{patch}\n```")
    if skipped:
        parts.append(
            f"{skipped} diff(s) were left out. Use get_file_contents with "
            f"ref={pr['head']['sha']} to read those files."
        )
    parts.append(
        "Review for correctness bugs, security problems, missing tests and readability. "
        "Name the file and line for each point. To see more context, use get_file_contents "
        f"with ref={pr['head']['sha']}. End with a verdict: approve, request changes, or "
        "comment."
    )
    return "\n\n".join(parts)
  • A prompt that does work: it fetches the PR and the diff of every changed file, so the model starts with full context instead of spending several tool calls first.
  • ctx: Context works in prompts and resources just like in tools.
  • /pulls/{n}/files is a list (up to 3,000 files), so it reuses get_paginated from step 4. more_files adds a + to the count when there are more than 100.
  • number: int: prompt arguments always arrive as strings; the SDK converts "7" to 7 from the type hint.
  • The diff budget (MAX_DIFF_CHARS) is the same context guard as max_chars in step 3. Diffs that don't fit are left out and the prompt says so, pointing to get_file_contents, like truncated and has_more.
  • ref={pr['head']['sha']}: the exact commit at the tip of the PR, so the model reads the code as the PR changes it.
  • f.get("patch") or ...: GitHub omits patch for binary or huge files.
  • Why MCPError? For prompts, the SDK replaces any other exception with a vague "Internal server error". MCPError passes through unchanged, so the user sees "Not found...". INVALID_PARAMS (-32602) for 4xx and INTERNAL_ERROR (-32603) for 5xx are standard JSON-RPC error codes.
  • "\n\n".join(parts): building a list then joining once is cleaner and faster than adding strings in a loop.

4.7 Why test this way

  • Every test goes through the real MCP path (Client → tools/call → our function), not by calling functions directly. That way the tests also cover tool registration, schemas, validation and error conversion.
  • Each guard has its own test. A guard nobody tests tends to break quietly when code changes.
  • Success and failure paths. Most bugs in API integrations hide in the error handling, so roughly half the tests are failure cases.
  • Fast and offline. The whole suite runs in about a second with no internet or token, so you can run it after every change, and later in CI (step 7).

4.9 Continuous integration (step 7)

What CI is, and why it matters

Continuous integration means every change is automatically built and tested on a clean machine, not just on your laptop. It catches:

  • "works on my machine" problems (a file you forgot to commit, a package only installed locally),
  • problems on Python versions or operating systems you didn't try,
  • style drift and lint errors, before anyone reviews the code.

GitHub Actions is GitHub's built-in CI. A workflow is a YAML file in .github/workflows/. It contains jobs (each runs on a fresh virtual machine, a runner), and each job has steps (shell commands or reusable actions).

The workflow, line by line (.github/workflows/ci.yml)

name: CI

on:
  push:
    branches: [main]
  pull_request:
  • on: the triggers. Every push to main, and every pull request (from any branch). A PR is checked before it's merged.
permissions:
  contents: read
  • Least privilege again. Each run gets a temporary token; this limits it to reading the code. If a dependency were ever compromised, it couldn't push code or change settings.
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
  • If you push twice quickly, the first run is cancelled. Its result would be out of date anyway, and it saves CI minutes.

The lint job

  lint:
    name: Lint (ruff)
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
        with:
          enable-cache: true
      - name: Install dependencies (exact versions from uv.lock)
        run: uv sync --locked
      - name: Lint
        run: uv run ruff check .
      - name: Check formatting
        run: uv run ruff format --check .
  • runs-on: ubuntu-latest: a fresh Linux machine for every run. Nothing is left over from earlier runs.
  • timeout-minutes: 10: a stuck job is killed instead of running for the default 6 hours.
  • actions/checkout@v4: downloads your repository onto the runner.
  • astral-sh/setup-uv@v6: installs uv. enable-cache: true caches downloaded packages between runs, so later runs are faster.
  • @v4, @v6: actions are pinned to a major version, so a breaking change in an action can't silently break CI. (Stricter still is pinning to a full commit SHA; Dependabot, below, keeps these up to date either way.)
  • uv sync --locked: installs the exact versions in uv.lock, and fails if uv.lock doesn't match pyproject.toml. That catches the classic mistake of adding a dependency without committing the updated lock file.
  • ruff format --check: doesn't change files, only fails if any file isn't formatted. Locally you run uv run ruff format . to fix it.

The test job and the matrix

  test:
    name: Tests (Python ${{ matrix.python-version }}, ${{ matrix.os }})
    runs-on: ${{ matrix.os }}
    timeout-minutes: 10
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        python-version: ["3.11", "3.12", "3.13"]
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
        with:
          python-version: ${{ matrix.python-version }}
          enable-cache: true
      - name: Install dependencies (exact versions from uv.lock)
        run: uv sync --locked
      - name: Run tests with coverage (fails under 90%)
        run: uv run pytest --cov --cov-report=term-missing
  • A matrix runs the same job for every combination: 2 operating systems × 3 Python versions = 6 jobs in parallel.
  • Why Windows? You develop on Windows and most CI only tests Linux. Paths, line endings and encodings differ, and this catches those bugs.
  • Why 3.11 to 3.13? pyproject.toml promises requires-python = ">=3.11". The matrix proves that promise is true, from the oldest version you claim to support to the newest.
  • "3.11" in quotes: in YAML, 3.10 unquoted would become the number 3.1. Quoting versions is a habit worth having.
  • fail-fast: false: by default one failing job cancels the rest. Turning that off shows the whole picture, e.g. "fails only on Windows".
  • No secrets needed: the tests mock GitHub with respx, so CI never needs your token. This is a big benefit of mocking: secrets never go near CI.

I checked the workflow with actionlint (a linter for GitHub Actions files) and ran the same commands here with Python 3.11, 3.12 and 3.13: all pass.

Coverage

[tool.coverage.run]
source = ["github_mcp"]
branch = true

[tool.coverage.report]
show_missing = true
skip_covered = true
fail_under = 90
  • Coverage measures which lines of your code ran during the tests (pytest-cov is the pytest plugin for the coverage tool).
  • branch = true: also checks that both sides of each if were taken, not just that the line ran. Stricter and more honest.
  • fail_under = 90: the test run fails if coverage drops below 90%. It's a ratchet: new code must come with tests. We're at about 93% now.
  • show_missing: lists the line numbers that never ran, so you know where tests are missing.

4.10 Deployment: HTTP mode, Docker and the demo (step 8)

stdio vs Streamable HTTP

MCP defines how messages (JSON-RPC) travel between client and server. That's the transport. There are two that matter:

stdio Streamable HTTP
Who starts the server The client starts it as a child process It runs on its own, as a service
How they talk stdin / stdout HTTP POST to one endpoint (/mcp)
How many clients Exactly one Many, possibly on other machines
Security Nothing listens on the network Anyone who can reach the port can call it
Typical use Claude Desktop, Claude Code on your laptop A shared team server, a container, the cloud

Until now we only had stdio. It's the right default (simplest, safest), so it stays the default. HTTP is opt-in: MCP_TRANSPORT=http.

The key insight: the tools, resources and prompts don't change at all. Only the way bytes arrive changes. That's why server.py needed just a few lines: the transport is a separate layer, which is exactly the point of MCP's design.

def main() -> None:
    logger.info("Starting GitHub MCP server v%s (%s)", __version__, settings.transport)
    if settings.transport == "http":
        from github_mcp.http_app import serve

        serve(settings)
    else:
        mcp.run()  # stdio: the client starts this process and talks over stdin/stdout

The import is inside the if so stdio users never load the web server code.

The new problem: the network

With stdio, only the program that started the server can talk to it. With HTTP, anyone who can reach the port can, and every request uses your GitHub token. So http_app.py adds three guards.

Guard 1: loopback by default

MCP_HOST defaults to 127.0.0.1 (loopback: only programs on the same computer can connect). 0.0.0.0 means "every network interface", which is what a container needs (see below) but is dangerous on a laptop on public Wi-Fi.

Guard 2: a bearer token, required off loopback

if settings.http_host not in LOOPBACK_HOSTS and settings.auth_token is None:
    raise RuntimeError(f"Refusing to listen on {settings.http_host} without MCP_AUTH_TOKEN: ...")
  • Fail closed: an unsafe configuration doesn't start with a warning nobody reads, it refuses to start, with a message saying how to fix it. The same philosophy as writes being off by default.
  • Clients send Authorization: Bearer <token>. A bearer token means "whoever bears (holds) this token is allowed in", like a ticket.

The check is a small ASGI middleware. ASGI is the standard interface between Python web servers (uvicorn) and web apps (Starlette): an app is just async def app(scope, receive, send). A middleware is an app that wraps another app and decides whether to pass the request on:

async def __call__(self, scope, receive, send):
    if scope["type"] != "http" or scope["path"] in PUBLIC_PATHS:
        await self.app(scope, receive, send)        # lifespan events and /health pass
        return
    supplied = dict(scope["headers"]).get(b"authorization", b"")
    if hmac.compare_digest(supplied, self._expected):
        await self.app(scope, receive, send)        # right token: through
        return
    ...send a 401 with "WWW-Authenticate: Bearer"
  • hmac.compare_digest, not ==: == stops at the first different character, so a wrong guess that starts correctly takes slightly longer. Measured over many requests, that leaks the token one character at a time (a timing attack). compare_digest always takes the same time.
  • 401 Unauthorized with WWW-Authenticate: Bearer is the standard HTTP way to say "you need a bearer token".
  • Why not OAuth? The SDK supports full OAuth 2.1, which is the right choice for a public multi-user service (each user logs in, gets their own scopes). For a single-owner server, a shared secret is simpler and adequate. Knowing when each is appropriate is the interview point.

Guard 3: DNS rebinding protection

A subtle browser attack: you visit evil.example. Its page makes your browser send requests to evil.example, then the attacker changes the DNS record of evil.example to point to 127.0.0.1. Your browser now sends requests to your local server, but still with Host: evil.example. The defence is to refuse any request whose Host header isn't one we expect:

security = TransportSecuritySettings(
    enable_dns_rebinding_protection=True,
    allowed_hosts=["127.0.0.1:*", "localhost:*", "[::1]:*"] + settings.allowed_hosts,
    ...
)

The SDK enables this automatically only when the host is loopback; in a container the host is 0.0.0.0, so we turn it on explicitly. A refused request gets 421 Misdirected Request. MCP_ALLOWED_HOSTS adds names when you deploy behind a real domain.

Stateless and JSON

app = mcp.streamable_http_app(stateless_http=True, json_response=True, ...)
  • Stateless: each request stands alone; the server keeps no session between requests. Any copy of the server can answer any request, so you can run several behind a load balancer, and a restart loses nothing. We can do this because our server has no per-session state (no subscriptions, no server-to-client requests).
  • JSON responses: Streamable HTTP can answer with a stream of events (SSE) for long-running work with progress updates. Our tools answer in one go, so plain JSON is simpler to call and to debug with curl.
  • The GitHub client is still created once at startup: the SDK's session manager enters our lifespan once, not per request.

/health

@mcp.custom_route("/health", methods=["GET"])
async def health(_request: Request) -> JSONResponse:
    return JSONResponse({"status": "ok", "version": __version__})

A liveness check: Docker, Kubernetes and load balancers poll it to know the process is alive. It needs no token (it reveals nothing) and calls nothing (it must be cheap and must not use the GitHub rate limit).

"""A small async wrapper around the GitHub REST API.

All HTTP details live here (base URL, auth, headers, timeouts, error mapping), so
tools in server.py only ever deal with Python data and one exception type.
"""

import asyncio
import logging
import random
import time
from collections.abc import Callable
from typing import Any

import httpx

from github_mcp import __version__
from github_mcp.config import Settings

# Hard stop on how many pages one tool call may fetch, whatever the model asks for.
MAX_PAGES = 5

# Retries: only for failures that may succeed on a second try (network, timeouts, 5xx).
MAX_ATTEMPTS = 3  # the first try plus two retries
BASE_DELAY_S = 0.5  # backoff ceiling doubles each time: 0.5s, then 1s
RETRYABLE_STATUS = {500, 502, 503, 504}

# A tool call should never hang for minutes. Longer rate-limit waits are reported instead.
MAX_WAIT_S = 10.0

logger = logging.getLogger("github_mcp.github_client")

# Indirection so tests can replace sleeping with a recorder and run instantly.
_sleep = asyncio.sleep


class GitHubAPIError(Exception):
    """A GitHub API call failed. The message is written to be read by the model."""

    def __init__(self, status_code: int, message: str):
        super().__init__(message)
        self.status_code = status_code


class GitHubClient:
    def __init__(self, settings: Settings):
        headers = {
            "Accept": "application/vnd.github+json",
            "X-GitHub-Api-Version": "2022-11-28",
            "User-Agent": f"github-mcp-server/{__version__}",
        }
        if settings.github_token is not None:
            headers["Authorization"] = f"Bearer {settings.github_token.get_secret_value()}"

        # One AsyncClient for the whole server lifetime: it keeps a pool of
        # TCP/TLS connections open, so repeated calls skip the handshake.
        self._http = httpx.AsyncClient(
            base_url=settings.github_api_url,
            headers=headers,
            timeout=settings.request_timeout_s,
        )
        self._authenticated = settings.github_token is not None

    async def get(self, path: str, params: dict[str, Any] | None = None) -> Any:
        response = await self._request("GET", path, params=params)
        return response.json()

    async def post(self, path: str, json: dict[str, Any]) -> Any:
        """Send a POST (it creates something on GitHub). Never retried after a network
        error or 5xx, because the first attempt may already have succeeded."""
        response = await self._request("POST", path, json=json)
        return response.json()

    async def get_paginated(
        self,
        path: str,
        params: dict[str, Any] | None = None,
        *,
        max_items: int,
        keep: Callable[[dict[str, Any]], bool] = lambda item: True,
    ) -> tuple[list[dict[str, Any]], bool]:
        """Collect up to max_items from a list endpoint, following GitHub's Link headers.

        Returns the items and whether more exist beyond what we returned. `keep` filters
        items as they arrive (e.g. dropping pull requests from the issues endpoint).
        """
        url: str | None = path
        query = {**(params or {}), "per_page": min(100, max(max_items, 1))}
        items: list[dict[str, Any]] = []

        for _ in range(MAX_PAGES):
            response = await self._request("GET", url, params=query)
            items.extend(item for item in response.json() if keep(item))
            url = response.links.get("next", {}).get("url")
            # Our token is sent with every request, so only follow links back to GitHub.
            if url is not None and not url.startswith(str(self._http.base_url).rstrip("/") + "/"):
                url = None
            # The "next" URL already carries every query parameter.
            query = None
            if url is None or len(items) >= max_items:
                break

        has_more = len(items) > max_items or url is not None
        return items[:max_items], has_more

    async def _request(
        self,
        method: str,
        url: str,
        *,
        params: dict[str, Any] | None = None,
        json: dict[str, Any] | None = None,
    ) -> httpx.Response:
        """Send a request with retries. Returns a successful response or raises GitHubAPIError.

        Retried: timeouts, network errors and 5xx, but only for GET, which is idempotent.
        Rate limits: wait if GitHub asks for a short pause, otherwise explain and stop.
        (A rate-limited request was rejected, so repeating it is safe for any method.)
        Not retried: other 4xx errors, because the same request would fail the same way.
        """
        idempotent = method == "GET"
        for attempt in range(1, MAX_ATTEMPTS + 1):
            try:
                response = await self._http.request(method, url, params=params, json=json)
            except httpx.TimeoutException as exc:
                error = GitHubAPIError(504, f"GitHub did not respond in time ({url}).")
                error.__cause__ = exc
            except httpx.HTTPError as exc:
                error = GitHubAPIError(502, f"Could not reach GitHub: {exc}")
                error.__cause__ = exc
            else:
                if response.is_success:
                    return response

                wait = _rate_limit_wait(response)
                if wait is not None:
                    if wait > MAX_WAIT_S or attempt == MAX_ATTEMPTS:
                        raise GitHubAPIError(response.status_code, self._rate_limit_message(wait))
                    logger.warning("Rate limited by GitHub; waiting %.1fs before retrying", wait)
                    await _sleep(wait)
                    continue

                error = GitHubAPIError(response.status_code, _error_message(response))
                if response.status_code not in RETRYABLE_STATUS:
                    raise error

            if not idempotent:
                # The request may have reached GitHub before the failure; a repeat could
                # create a duplicate. Let the caller (the model) check and decide.
                raise GitHubAPIError(
                    error.status_code,
                    f"{error} The {method} was not retried because it may already have "
                    "succeeded. Check before trying again.",
                ) from error.__cause__

            if attempt == MAX_ATTEMPTS:
                raise GitHubAPIError(
                    error.status_code, f"{error} Gave up after {MAX_ATTEMPTS} attempts."
                ) from error.__cause__

            # Exponential backoff with full jitter: a random wait up to 0.5s, then up to 1s.
            # The randomness stops many clients retrying at the same instant.
            delay = random.uniform(0, BASE_DELAY_S * 2 ** (attempt - 1))
            logger.warning("Attempt %d failed (%s); retrying in %.2fs", attempt, error, delay)
            await _sleep(delay)

        raise AssertionError("unreachable")  # the loop always returns or raises

    def _rate_limit_message(self, wait_s: float) -> str:
        minutes = max(1, round(wait_s / 60))
        message = (
            f"GitHub rate limit reached. It resets in about {minutes} minute(s). "
            "Retrying now will not help; tell the user and try again later."
        )
        if not self._authenticated:
            message += " Adding a GITHUB_TOKEN raises the limit from 60 to 5,000 requests/hour."
        return message

    async def aclose(self) -> None:
        await self._http.aclose()


def _rate_limit_wait(response: httpx.Response) -> float | None:
    """Seconds GitHub wants us to wait, or None if this error is not a rate limit."""
    if response.status_code not in (403, 429):
        return None
    retry_after = response.headers.get("retry-after")
    if retry_after is not None:  # secondary rate limit: GitHub says exactly how long
        try:
            return max(0.0, float(retry_after))
        except ValueError:
            return 60.0
    if response.headers.get("x-ratelimit-remaining") == "0":  # hourly budget used up
        try:
            return max(0.0, int(response.headers["x-ratelimit-reset"]) - time.time())
        except (KeyError, ValueError):
            return 60.0
    if response.status_code == 429:  # no hint given; GitHub's docs say wait a minute
        return 60.0
    return None  # a 403 without rate-limit headers is a permissions problem

@mcp.prompt(title="Review a pull request")
async def review_pull_request(owner: str, repo: str, number: int, ctx: Context) -> str:
    """Review a pull request. The PR's description and changed lines are loaded for you."""
    github = _github(ctx)
    try:
        pr = await github.get(f"/repos/{owner}/{repo}/pulls/{number}")
        files, more_files = await github.get_paginated(
            f"/repos/{owner}/{repo}/pulls/{number}/files", max_items=100
        )
    except GitHubAPIError as exc:
        # Prompts have no "isError" result like tools, so failures travel as a protocol
        # error. MCPError keeps our readable message (any other exception is hidden as
        # "Internal server error").

        f"{author}, merging {pr['head']['ref']} into {pr['base']['ref']}."
    )

        f"Description:\n{pr.get('body') or '(no description)'}",
        f"Changed files ({len(files)}{'+' if more_files else ''}):",
    ]
    budget = MAX_DIFF_CHARS
    skipped = 0
    for f in files:
        header = f"### {f['filename']} ({f['status']}, +{f['additions']} -{f['deletions']})"
        patch = f.get("patch") or "(no text diff: binary or very large file)"
        if len(patch) > budget:
            skipped += 1
            parts.append(f"{header}\n(diff left out to keep this prompt short)")
            continue
        budget -= len(patch)
        parts.append(f"{header}\n```diff\n{patch}\n```")
    if skipped:
        parts.append(
            f"{skipped} diff(s) were left out. Use get_file_contents with "
            f"ref={pr['head']['sha']} to read those files."
        )
    parts.append(
        "Review for correctness bugs, security problems, missing tests and readability. "
        "Name the file and line for each point. To see more context, use get_file_contents "
        f"with ref={pr['head']['sha']}. End with a verdict: approve, request changes, or "
        "comment."
    )

def _decode_text(raw: bytes) -> str | None:
    """Return the bytes as UTF-8 text, or None if they look like a binary file."""
    if b"\x00" in raw:  # text files practically never contain null bytes
        return None
    try:
        return raw.decode("utf-8")

"""Streamable HTTP mode: the same MCP server, reachable over the network.

stdio is enough when the MCP client starts the server itself (Claude Desktop, Claude Code).
HTTP is for running it as a service, for example in a Docker container. That raises
security questions stdio never has, because anyone who can reach the port can use your
GitHub token through it. So this module adds three guards:

1. Loopback by default: it listens on 127.0.0.1 unless told otherwise.
2. A bearer token (MCP_AUTH_TOKEN), required before it will listen on any other address.
3. DNS rebinding protection: requests whose Host header isn't on the allow list are refused,
   so a web page in your browser can't talk to the server through a hostile domain name.
"""

import hmac
import json
import logging

from mcp.server.transport_security import TransportSecuritySettings
from starlette.types import ASGIApp, Receive, Scope, Send

from github_mcp.config import Settings
from github_mcp.server import mcp

logger = logging.getLogger(__name__)

LOOPBACK_HOSTS = {"127.0.0.1", "localhost", "::1"}
DEFAULT_ALLOWED_HOSTS = ["127.0.0.1:*", "localhost:*", "[::1]:*"]
PUBLIC_PATHS = {"/health"}  # reachable without the bearer token


class BearerTokenMiddleware:
    """Reject HTTP requests that don't carry "Authorization: Bearer <token>".

    Written as plain ASGI (a callable taking scope, receive, send) so it wraps any app.
    """

    def __init__(self, app: ASGIApp, token: str) -> None:
        self.app = app
        self._expected = f"Bearer {token}".encode()

    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
        if scope["type"] != "http" or scope["path"] in PUBLIC_PATHS:
            await self.app(scope, receive, send)
            return
        supplied = dict(scope["headers"]).get(b"authorization", b"")
        # compare_digest takes the same time whether the first or last byte differs,
        # so an attacker can't guess the token one character at a time by timing replies.
        if hmac.compare_digest(supplied, self._expected):
            await self.app(scope, receive, send)
            return
        body = json.dumps({"error": "Missing or wrong bearer token."}).encode()
        await send(
            {
                "type": "http.response.start",
                "status": 401,
                "headers": [
                    (b"content-type", b"application/json"),
                    (b"www-authenticate", b"Bearer"),
                ],
            }
        )
        await send({"type": "http.response.body", "body": body})


def build_app(settings: Settings) -> ASGIApp:
    """Build the HTTP app, refusing unsafe combinations of settings."""
    if settings.http_host not in LOOPBACK_HOSTS and settings.auth_token is None:
        raise RuntimeError(
            f"Refusing to listen on {settings.http_host} without MCP_AUTH_TOKEN: anyone who "
            "can reach this address could use your GitHub token. Set MCP_AUTH_TOKEN, or use "
            "MCP_HOST=127.0.0.1."
        )
    allowed_hosts = DEFAULT_ALLOWED_HOSTS + settings.allowed_hosts
    security = TransportSecuritySettings(
        enable_dns_rebinding_protection=True,
        allowed_hosts=allowed_hosts,
        allowed_origins=[f"http://{h}" for h in allowed_hosts],
    )
    app = mcp.streamable_http_app(
        # Stateless: every request stands alone, so any copy of the server can answer it
        # and nothing is lost on restart. This server keeps no per-session state anyway.
        stateless_http=True,
        # Plain JSON replies instead of an event stream: simpler to call and to debug.
        json_response=True,
        transport_security=security,
        host=settings.http_host,
    )
    if settings.auth_token is None:
        logger.warning("HTTP mode without MCP_AUTH_TOKEN: only safe on 127.0.0.1")
        return app
    return BearerTokenMiddleware(app, settings.auth_token.get_secret_value())


def serve(settings: Settings) -> None:  # pragma: no cover - starts a real network server
    import uvicorn

    try:
        app = build_app(settings)
    except RuntimeError as exc:
        logger.error("%s", exc)  # a clear one-line reason instead of a traceback
        raise SystemExit(1) from None
    logger.info("Serving MCP on http://%s:%d/mcp", settings.http_host, settings.http_port)
    uvicorn.run(app, host=settings.http_host, port=settings.http_port, log_level="info")
